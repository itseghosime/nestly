## 0. How to read this document

Each feature row follows the mandated mapping:

> **Feature → Current UI behavior → Required data → Permissions → Backend operation → Integration → Acceptance test**

- **Current UI behavior** is what the frontend does today (local fixtures, localStorage, simulated toasts/modals, no network).
- **Required data** is the minimal canonical record the backend must own; field names align with `lib/types.ts` and `lib/fixtures/*` where present, otherwise with Blueprint Chapter 07's "Suggested core database tables."
- **Permissions** are expressed as authenticated roles; anonymous public vs. authenticated staff with role boundaries per Blueprint Chapter 07.
- **Backend operation** is the state transition or query the backend must expose (idempotent where required).
- **Integration** lists the external provider or internal subsystem the operation must touch (or explicitly *none*).
- **Acceptance test** is an observable, failure-aware test that would satisfy Blueprint Chapter 10's R01–R15 and Chapter 08's failure matrix.

Rows are tagged with provenance:

- **(DOC)** — requirement is explicit in Blueprint, Workflow PNG, or Infographic PNG.
- **(DEMO)** — behavior exists only as a frontend mock with no specification and must not be treated as contractual without approval.

Contradictions and open decisions are collated in §7 and §8. Nothing in §1–§6 should be read as permission to copy demo behavior into production without the approval step the Blueprint requires (Chapter 13 — "becomes the team's development contract once open decisions are approved").

## 8. Contradictions & missing decisions

### 8.1 Contradictions that must be resolved before build

1. **Legal/Agency fee arithmetic diverges three ways.** Blueprint Ch.06 requires `agency and caution fees` disclosures; UI detail page computes `legal = rent*0.1` and `agency = rent*0.1` with `caution=200k` / `service=300k` constants; `PropertyEditor` computes `legal = rent*0.05`. No chapter fixes the rate. **Decision required:** canonical ledger (`legalPct`, `agencyPct`, `cautionFormula`, `serviceFormula`) and whether caution is flat or a function of rent.

2. **WhatsApp provider diverges.** BUILD_LOG §6 proposes *Twilio WhatsApp or Meta Cloud API*; Infographic specifies *Meta Cloud API (test)*; `S17` Integrations grid lists **both** Twilio WhatsApp (Nia AI Endpoint, `180ms`) and Meta Cloud API Official Channel (`sandbox_simulation`, `220ms`) with identical "Operational" badges. **Decision required:** single provider for production; the other card must move to `Simulation` or be removed.

3. **Database conflict guard has no single source.** `availability` page locally appends slots with no `409`; Chapter 08 requires atomic slot validation and Chapter 10 "database conflict checks/constraint." Google Calendar is named as optional in Ch.10 but also as an inspected fake integration in `S17`. **Decision required:** Supabase `EXCLUDE`/`UNIQUE` constraint is the source of truth; Calendar sync (if any) is downstream projection only.

4. **Audit pagination is declared but not implemented.** `S16` footer claims `Page 1/25` of `148` with next/prev controls, but `GET` returns a full array and paging is visual-only. Blueprint Ch.07 requires viewable audit with category/time filters (R13). **Decision required:** keyset pagination spec (`created_at, id` cursor + `limit`) or offset, and CSV streaming contract.

5. **Offers are required but have zero frontend.** R07 + Workflow step 5 mandate `OFFER_PENDING → approved/rejected/countered` with human authority; frontend has no offer form, amount field, or staff Offers queue. **Decision required:** whether to add an Offers module before R07 can be exercised, or explicitly descope R07 from this phase.

### 8.2 Missing decisions that block schema freeze

- **Nia model & budget:** "AI model (OpenAI or similar)" (Ch.11) with no model name, token cap, grounding tool allowlist, or cost alert. Blueprint Ch.13 leaves this as "must still confirm." Without it, `@gsap/react` vs. AI cost is decoupled but backend cannot provision the model.
- **Message retention & expiry:** "Define retention limits, collect only needed contact details" (Ch.07) and `context expiry` in Ch.05. No TTL value; fixtures use `Yesterday 16:40 WAT` strings with no `expires_at`.
- **Inspection slot capacity & corridor mapping:** `capacity` is numeric but `assignedZone` is free text; Blueprint R09 expects travel/capacity validation. No capacity ceiling or travel matrix is specified.
- **Notification channels:** Resend is stated, Termii SMS is slated, but which events trigger which channel (email vs. SMS vs. in-app) is not enumerated. S12 fixtures show 4 types but no delivery SLAs.
- **Auth roles hierarchy:** fixtures list five roles; `S13` invite allows only three. `Platform Admin` vs. `Customer Care` visibility is not defined.
- **Property verificationBadge source:** `Verified Physical Title | Vetted Landlord | Direct Instruction` is an enum in `lib/types.ts` but has no state machine (who sets it, what evidence moves it).
- **Fee `last verified date`:** Blueprint Ch.06 lists it as minimum information; fixtures omit it entirely.

No row in §1–§6 invents an answer to the above; each is recorded as **TBD** for the approval session that must precede any backend PR.

## Appendix A — Corrections applied 2026-10-17 (CORRECTED per §3/§4 of the backend authorization)

This appendix records the 13 corrections mandated before implementation, each with provenance and concrete schema/API consequence. It is the normative correction of the trace; §1–§11 remain valid where consistent, and this appendix prevails where they diverge. Treat this as the latest direction where older documents conflict.

### A.1 Publication vs. rental availability vs. verification vs. inspection availability — separate states

- **Correction:** Four orthogonal columns replace the overloaded `status` / `inspectionStatus` conflation inherited from fixtures.
  - `properties.publication_state` enum(`draft`,`review`,`published`,`archived`) — controls CMS lifecycle and public visibility gate.
  - `properties.rental_availability` enum(`available`,`reserved`,`rented`,`unavailable`) — controls whether a listing is bookable.
  - `properties.verification_state` enum(`unverified`,`vetted`,`verified`) — controls trust badge evidence; transitions require `verification_events` rows.
  - `inspection_availability` — **derived**, not stored: `EXISTS (SELECT 1 FROM inspection_slots WHERE property_id = properties.id AND status='available' AND starts_at > now())`.
- **Public gate:** `public_properties` view returns rows only where `publication_state='published' AND rental_availability IN ('available') AND verification_state IN ('vetted','verified')`. This preserves Blueprint Ch.06 "Do not recommend rented" without conflating it with draft/review.
- **Migration mapping:** `lib/fixtures/properties.ts` maps `status=Draft→draft, In Review→review, Available→published+available, Rented→published+rented`; `inspectionStatus=Instant Booking|Slots Available|Waitlist` maps to `rental_availability` + initial `inspection_slots` seed; `verificationBadge` maps to `verification_state`.

### A.2 Public responses exclude private data

- **Correction:** `public_properties` view and `GET /api/properties/:id` public projection **exclude** `landlord_contact` private fields (`phone`,`email`,`full_address` beyond `addressShort`), `customers` PII (`phone`,`email`,`notes`), and `audit_events` internals (`ip_address`,`raw_payload`,`deltaBefore/After`). These fields are available only via authenticated staff projections (`/api/properties/:id?scope=staff` or staff RLS). This satisfies §3.2 and Blueprint Ch.07 privacy.

### A.3 Canonical IDs, stable public references, fixture mapping

- **Correction:** Keep existing fixture IDs (`prop-gra-01`,`cust-101`,`insp-501`,`EV-*`) as primary keys for migration continuity. Add `properties.fixture_id TEXT UNIQUE` + `fixture_id_map(fixture_id, canonical_id, entity)` for any n8n WF01 references that used legacy IDs. Add `bookings.public_reference TEXT UNIQUE` (`NST-YYYY-XXXX`) and `bookings.access_token UUID UNIQUE DEFAULT gen_random_uuid()` for receipt/status links. URLs never carry PII blobs — only `?token=<uuid>` or verified session.

### A.4 Timestamps are timestamptz; display in Africa/Lagos

- **Correction:** Every `created_at`, `updated_at`, `starts_at`, `ends_at`, `reserved_until`, `timestamp` column is `timestamptz` stored in UTC. Display uses `AT TIME ZONE 'Africa/Lagos'` or `Intl.DateTimeFormat('en-NG',{timeZone:'Africa/Lagos'})` yielding `WAT`. Fixture strings like `"17 Oct 2026, 09:42 WAT"` are parsed to `timestamptz` on seed.

### A.5 Money is precise with explicit currency

- **Correction:** `properties.rent_annual NUMERIC(12,2) NOT NULL` + `currency CHAR(3) DEFAULT 'NGN' CHECK (currency IN ('NGN','USD','GBP'))`. `priceFormatted` is a **derived** DB function `format_price(rent_annual,currency)` and API-computed view column, never a stored int. All `offers.amount`, `property_fees.amount` are `NUMERIC(12,2)`. No `INT` price columns remain.

### A.6 Slot overlaps via start/end + database exclusion

- **Correction:** `inspection_slots` uses `(starts_at TIMESTAMPTZ, ends_at TIMESTAMPTZ)` with `EXCLUDE USING gist (property_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&)` and a second exclusion per `field_agent_id` (where `field_agent_id IS NOT NULL AND status IN ('available','booked')`). `UNIQUE(property_id,date,time_range)` is **removed** — it does not prevent overlaps. `transit_buffer_mins` from `workspace_settings` is added to `ends_at` in the application overlap check and via a second exclusion variant. All temporal checks are server-side SQL, not client `Array.filter`.

### A.7 Supabase Auth owns passwords/tokens — no shadow store

- **Correction:** No `password_hash` column in `profiles`; no direct writes to `auth.users`. Staff profiles are `profiles(id UUID PK FK auth.users, display_name, role, capabilities TEXT[], assigned_zone, created_at)` with RLS. Auth flows use only supported APIs: `signInWithPassword`, `signOut`, `resetPasswordForEmail`, `updateUser`, `inviteUserByEmail`, `verifyOtp`. Capability assignment is app data in `profiles.capabilities`, never in `auth.users` raw.

### A.8 Staff profiles & role/capability matrix are app data

- **Correction:** `profiles.role` / `profiles.capabilities` are the source of authorization. Documented in `docs/roles-matrix.md` (least-privilege: `user:promote` required to change `role`, `team:invite` to invite, `properties:write:any` to edit any listing). Self-promotion is blocked by RLS `WITH CHECK`.

### A.9 Current Twilio validation; direct Meta deferred

- **Current provider decision:** Twilio remains the WhatsApp provider while Meta verification is pending; direct Meta verification and ingress are deferred, not a prerequisite.
- **Required, not deployed:** Twilio POST signature validation must use `X-Twilio-Signature`, the exact public callback URL, all request parameters, and the Twilio Auth Token. Official n8n Cloud Code nodes cannot read credential values, so the documented compatible path is a validator proxy in the existing Next.js deployment, forwarding only valid requests to the existing WF01 Webhook protected by a separate Header Auth relay credential. This does not add another conversation or reply engine. It requires a separately stored app secret and a coordinated Twilio callback cutover; see `docs/n8n-contracts.md`.
- **Meta-specific future work:** Meta GET subscription verification (`hub.mode=subscribe` and `hub.verify_token` → `hub.challenge`) and POST signature verification (`X-Hub-Signature-256 = HMAC-SHA256(WHATSAPP_APP_SECRET, rawBody)`) are separate operations with separate configuration. These are not applicable to current Twilio ingress. Do not implement until Meta is re-enabled as an explicit provider decision.

### A.10 Customer messages stay customer-authored during takeover

- **Correction:** During `conversations.status='HUMAN_ACTIVE'`, `messages.sender='user'` rows continue to persist; only `sender='nia'` generation is suppressed. Suppression is checked at the **dispatch boundary** (n8n/AI checks `conversations.status` immediately before `sendMessage`), not at ingest. The UI label "`HUMAN_ACTIVE`" does not rewrite `sender`.

### A.11 Integration health is observed, not assumed

- **Correction:** `integrations.status` is `operational` only after a successful probe (`GET`/`HEAD` where endpoint+creds exist, latency measured). Missing credentials or no probe → `unconfigured`, transient failure → `degraded`. Never `Operational` by fixture default.
